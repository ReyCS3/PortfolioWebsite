Beach Circle

Getting through a day at CSULB means guessing: which lot still has spaces, whether any classroom is free to study in, where there's an outlet that works. Beach Circle is a Flutter app that turns those guesses into something you can check before you walk across campus.

Three features up close

Parking difficulty, without any sensors

CSULB has no per-space sensor hardware, so there is no ground-truth occupancy feed to read. The workaround is to measure the students instead of the spaces: the app counts how many users are actively searching a given lot against how many have marked themselves parked, and turns that ratio into a difficulty status on the map.

It is a crowdsourced signal, not a measurement, and the UI is deliberate about saying so — a lot reads Moderate rather than claiming a space count it cannot know.

  • Lot status derives from live counts of searching versus parked users, held in a parking_lots collection.
  • Filters narrow the sheet to a lot group — Pyramid, G lots, E lots, Palo Verde — instead of scrolling the whole campus.
  • Parking shares one map module with food alerts, bathrooms, outlets and pins, so all five features draw from the same pin rendering and zoom behaviour.

Food alerts that respect the off switch

Leftover catering is the most time-sensitive thing on a campus. A user with posting permission drops an alert with a title, description and location; it writes to Firestore, appears as a pin on the shared map, and pushes to every user who has food alerts switched on.

The half of this that actually took work was the other direction. A notification system is only trustworthy if turning it off works, so the preference check happens before the send, not in the client after delivery.

  • Alerts write to food_alerts and render on the map at their tagged building.
  • Delivery is gated on each user's stored notification preferences, per category.
  • Tapping a pin in the list jumps and zooms the map to that exact location.

One report pipeline for every kind of post

Beach Circle carries three forums, an event board and a feedback channel. Building a separate moderation flow for each would have meant four ways for the same bug to appear, so reports are polymorphic: one reports collection, with targetType and targetId pointing at whatever was flagged.

Each report stores the reason, free-text detail, both user IDs and a status that starts at open, which gives moderators a real queue to work rather than a pile of notifications.

  • Reporting is available on the event board, both forums, dorm life and feedback.
  • Moderator identity lives in its own moderators collection rather than a flag on the user document.
  • Moderators can put the app into maintenance mode when a fix needs to ship.

The test I'd point to first

Account A enables food alerts. Account B posts Free Pizza at the COB. A receives the push. A then turns food alerts off, B posts Free Cookies, and the alert is confirmed written to Firestore — but A's device stays silent.

Verifying that the feature fires is the easy half. Verifying that it stays quiet when a user has opted out is the half that catches real bugs, and it is the difference between a notification system people keep enabled and one they uninstall the app over.

The data model

Everything runs on a single Cloud Firestore database. Fifteen top-level collections, split roughly between campus resources, community content and account state.

  • users
  • moderators
  • reports
  • feedback
  • forumPosts
  • forumCategories
  • forum_requests
  • eb_events
  • dorm_events
  • food_alerts
  • parking_lots
  • outlets
  • study_halls
  • pins
  • demo_test_users

A live report document. targetType and targetId are what let one collection serve every surface in the app that accepts user content.

What I'd do differently

  • Settle the naming convention on day one. forumPosts and forumCategories are camelCase while food_alerts, parking_lots and study_halls are snake_case. Five people writing queries against inconsistent collection names is a small tax paid on every single feature, and it costs nothing to fix in week one.
  • Keep test fixtures out of the production database. demo_test_users sits alongside real data. It should have lived in a separate Firebase project, or been seeded and torn down by an emulator, so that no query ever has to remember to exclude it.
  • Measure the thing we claimed. We verified behaviour thoroughly and performance not at all — no read counts, no cold-start timings, no query profiling. On a Firestore app, reads are the bill, and I'd instrument that from the start next time.
